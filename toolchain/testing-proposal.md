# Testing proposal — 19 October 2026

**Implementation update:** See [testing.md](testing.md) for the suite built from this proposal, commands and current coverage limits. The proposal below is retained as the original design and historical case backlog.

**Original recommendation:** extend the existing Playwright and puzzle checks, add small logic tests and a real visual comparison layer, then make a dependable subset block deployment. Keep the static site architecture. This is a proposal; the wider suite and CI changes have not been built. Only focused regressions for the requested fixes were added now.

## Evidence and review scope

The complete reachable history was fetched (not a shallow checkout): **1,230 commits**, from 15 July to 19 October 2026, through `3a7598705060827245f603b43b923e44126c45a3`. Main was the only remote branch returned; no other branch or tag history was available. [testing-history.csv](testing-history.csv) inventories every commit's subject, date and affected scope. All subjects, bodies and changed-path lists were screened; relevant behavior changes were followed into patches and current code, including generic uploads that concealed fixes. This is not a claim that every generated puzzle or every line in all 1,230 patches was individually revalidated.

The history contains 609 generated-feed commits, 181 generic uploads, 46 file-operation subjects and 394 other described changes. The categories describe commit subjects, not quality or test coverage. Of these commits, 189 touch core files outside reports/generated lists and 385 touch games (overlapping counts). Retired behavior must not become a new requirement: use today's game rules and retain compatibility fixtures only where existing saves still need them. Pocket Weather is removed and needs no active release gate.

The history repeatedly exposes four risks: a result or save changes on reopen; an incidental touch triggers a second action; a date, random seed or cache is inconsistent; controls work on one screen but become unreachable on another. Those should shape the suite.

## Existing foundation and current baseline

| Existing check | What it contributes | Gap to address |
| --- | --- | --- |
| `tools/tests/run.js`, `play.js`, `harness.js` | Real puzzle play, result/share paths, saves, tracker reads, touch input, some first-paint and geometry checks | Scattered commands, date fixtures need discipline; no single pinned installation or release gate |
| `tools/tests/shots.js` | Screenshot capture | Captures are not an approved-baseline visual comparison suite |
| `tools/tests/sw.js` | Real local service worker, offline fallback, network-first, hung network and kill switch | Headless notification observation requires a supported environment or a separately reported device check |
| `tools/tests/timing-dates.js`, `offline-next.js` | Start-card clocks, London completion dates, interrupted downloads and dated Next list | Focused regressions, not exhaustive boundary/network coverage |
| `tools/tests/push-crypto.mjs`, `push-panel.js` | Encryption/signing and hidden opt-in UI | Do not imply live notification delivery is covered; sending remains off |
| Registry, clue, broad Doku and batch-generation checkers in `tools/` | Content structure, puzzle quality and uniqueness constraints | Need scoped fixtures, repeatable seeds, clear old-file exceptions and scheduled full-batch runs |
| News toolchain gates/harness | Metadata, editorial structure and article layout | Need deployed-artifact checks and targeted chart geometry tests; factual accuracy still needs editorial review |

Observed during this change: the main puzzle browser suite reports **288 passes and two existing date-punctuation failures** in Tangle/Borders home labels (expected “Sunday 18 October”, rendered “Sunday, 18 October”). The real-worker suite reports **15 passes and one failed notification observation** in this stripped headless Chromium environment. These are visible baseline issues, not new regressions or a green overall suite. The new offline/Next regressions pass separately: 18 assertions. Registry documentation records eight old July–August errors; inventory and reproduce them before accepting an exact, temporary exception list. Never ignore every error from an old date.

The current publishing workflow runs the finished-save check **after deployment**. Most browser/content checks do not block publication. Moving meaningful checks before deployment is as valuable as adding tests.

## Proposed layers

| Layer | Concrete purpose here | Proposed implementation |
| --- | --- | --- |
| Unit / logic | Date boundaries, scoring, save merges/migrations, timer accounting, deterministic game rules | Node's built-in test runner for small pure functions; extract only when it improves maintainability. No need to add Jest as well |
| Functional / integration | Real save + engine + finish sheet; build tools against a temporary report tree; tracker event contracts | Existing harness and temporary directories, controlled clocks/network, assert externally visible behavior |
| End to end | Start, play, finish, reopen, share, Next, board; complete/retry/resume each active game | Extend Playwright, use actual taps/keys for behavior under test. Seed/setup hooks may arrange state but must not run a different rules engine |
| Visual / accessibility | First paint, clipped controls, chart labels, overlay stacking, focus, readable results | Approved screenshot baselines plus DOM geometry, accessible-name/focus checks and an automated accessibility scan |
| Content / property | Many generated puzzles, random boards, stable identifiers and release dates | Existing independent solvers plus seeded samples and invariants; nightly exhaustive future-batch validation where practical |
| Backend | League permissions, first-result persistence, repeat backfills and hidden rows | Local or disposable Supabase with migrations and seeded identities; frontend mocks alone cannot verify SQL/RLS |

Prefer assertions such as “reopening keeps the original result and emits no second finish” over assertions that repeat an implementation line. A useful regression should fail against the relevant old behavior and pass today. Keep historical fixtures small, named and traceable to the commit below.

## Build order and release policy

1. **Make the baseline reproducible and trustworthy.** Add a small `package.json` and lockfile, pinned Playwright/browser versions, one documented command per group, fixed fonts, clocks, locales and seeds. Reconcile the two date-label assertions with intended copy. Resolve or explicitly report unsupported notification checks, and enumerate registry debt precisely. No blanket “ignore old errors” or retry-until-green. Separate tracker-contract tests from tests proving automation suppression.
2. **Gate the daily puzzle/site path first.** Logic/date/save tests, changed-content validation, start→finish→reopen/share for seven types, offline/Next regressions, feed navigation and deployed-artifact cutoff tests. Include archived full-page fixtures, not just shared engines. Run the actual transformed `_site` artifact in a smoke test; move gates before deploy and do not change source after the tested build. A build/rebase retry must rebuild and recheck the final revision.
3. **Protect all 11 active games.** One minimal real-input launch/play/pause/result/retry/save-resume flow per game, then the historical cases above. Use seeded model/property tests for scoring, conservation, generation and finite state; keep screenshots focused on controls/overlays. Do not require an entire long game run for every physics assertion.
4. **Add visual baselines and backend integration.** Begin with common finish/start screens, front pages and the historically fragile game overlays. Screens: small portrait 360×640, regular portrait 390×844 and short landscape 780×360, plus the specific 320×568 Lantern regression. Light/dark and reduced-motion representatives. Load the real pinned fonts; freeze animation only for static comparisons. First-paint/motion tests remain separate. Review baseline changes as code changes, with before/after/diff artifacts. Add isolated Supabase integration against actual SQL migrations with two leagues, owners/members/outsiders/admin and historical records.
5. **Broaden scheduled checks.** Nightly full future puzzle batches, larger seeded game runs, Chromium/WebKit/Firefox representatives, full visual matrix and backend tests. A small Android/iPhone installed-app release checklist covers real browser bars, touch, native share, fullscreen, wake lock and any future push delivery. Run read-only live-site smoke checks after deployment; keep a known-good commit/artifact for rollback.

For every pull request or main push: fast logic + changed-content checks and Chromium critical flows. Start with an aspirational **5–8 minute** budget and measure it; this is not a measured guarantee. Shared engine/frontend changes select all affected puzzle types; game changes select that game's cases; generator changes validate changed files plus boundary fixtures. Scheduled release of future-dated content must also run the gate even without a source change. Nightly heavier checks can aim for **15–30 minutes**, adjusted after measurement. SQL changes require the isolated backend suite before release.

A failed required check stops deployment. Upload failure traces, screenshots, visual diffs, seed/date and console/network errors so failures are reproducible. Retry only a genuinely transient setup/network failure with the original failure preserved. Use exact, owned, dated exceptions for known debt; a new failure is not automatically grandfathered. Each future bug fix should bring a small regression case linked to its defect/commit.

## Suggested first scope for discussion

Build steps 1 and 2 first, then add the game cases in risk order: finished saves/duplicate events, accidental taps, unreachable controls, and only then broader visual coverage. This provides confidence in daily publishing quickly while using the tests already present. Keep browser automation for behavior that needs a browser and cheap logic checks for everything else. No new hosting platform or paid test service is necessary to begin; measure CI time/storage before deciding whether paid capacity would help.

Open decisions: how much CI time is acceptable on each change; which physical phones are available for occasional checks; and whether to provision disposable Supabase testing now or in the backend phase. No broad testing framework, workflow rewrite or notification enablement is included in the current fixes.
