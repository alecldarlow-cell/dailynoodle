sections, publishing, saved progress, tracking). It is the one place these

## Identity
- Name: **The Daily Noodle** (formerly Digi News / Digi Puzzles / Digi Games, renamed 18 Oct 2026).
- Address: **https://dailynoodle.co.uk** (GitHub Pages, deployed by the build workflow, HTTPS enforced; `www.` redirects to it). Domain registered and DNS-hosted at Cloudflare, records "DNS only".

- **Puzzles only from 22 Nov 2026** (Alec's call): this site mirrors the app. News and Games moved to their own sites and repos, which publish on their own, outside this site's test gate: **https://news.dailynoodle.co.uk** (`alecldarlow-cell/dailynoodle-news`) and **https://games.dailynoodle.co.uk** (`alecldarlow-cell/dailynoodle-games`). ## Reckon: miles and imperial units (16 Nov 2026, Alec's call after a tester asked for miles)
- **What players see:** a two-way switch under the guess on every question with a convertible unit (`km | miles`, `m | feet`, `cm | inches`, `km² | sq miles`, `m² | sq ft`, `hectares | acres`, `km/h | mph`, `kg | lb`, `g | oz` (`lb` from 454 g), `tonnes | tons` (long tons), `litres | pints` (`gallons` from 20 litres), `ml | fl oz`). Flipping converts the question's unit phrase ("…, in miles?"; "in feet and inches?" when the answer is under 10 ft, or between 1 and 10 ft for a cm fact), the readout, the scale's labels, the answer, the note's figures and the recap. Feet and inches read "5 ft 6 in". It works mid-guess (the knob stays put: the guess moves to the nearest imperial rung) and on the reveal and the recap's review. Everyone starts in metric. **Stay metric:** °C (°F would change the percentage gap, so the score), mm, m/s, km/s, light years, every other unit, and any question that already names an imperial unit ("How many kilometres are in a mile?", the Mile High City, 70 mph stopping distance), about 10 facts. About 540 of the bank's 1,219 facts get the switch.
- **One remembered setting per kind** (distance, length, area, speed, weight, volume), so a player can keep miles for distances and metres for heights. Saved in `digi-reckon-v1` as two new keys (nothing renamed): `un` = `{dist:'i', len:'i', …}` (a kind is present only when imperial) and `unT` = the kinds whose one-off tip ("Lengths stay in feet and inches until you switch back.") has been shown. Not synced to the app (the app keeps its own).
- **Scoring is unchanged:** guesses are kept and scored in the fact's own metric unit (`R.cur`, `R.g`, `done[id].g`): an imperial rung is divided back by the factor. A constant factor leaves the ratio alone, so a guess scores the same either way (unit test UNITS-03 checks every rung of every fact). Share line, board and tracker are unchanged.
- **How:** display only, no change to the fact bank or any page. `engines/reckon.js` carries a pure `units` block (`/* units:start` … `/* units:end */`, `dnUnits`): `spec(q)` (kind, factor, labels, converted question and note), `rungs` (Ballpark's ladder in imperial; feet and inches round to whole inches), `parts`/`text` (number wording: 3 significant figures on the readout; a note keeps its own precision, one figure more for an exact figure, "a 3.8 km swim" → "a 2.36-mile swim"), `note` (figures, ranges "62 to 68 mph", "million"; a note that already gives imperial, such as "188 km (117 miles)", is left as written). The app's `src/features/puzzles/reckon/units.ts` is a port of this block, checked against a fixture written from it; change both together.
- **Tests:** unit `tools/tests/unit/reckon-units.test.js` (UNITS-01..06: which facts switch, every converted question, every rung scores as its metric, number wording, notes, the engine keeps metric); puzzle check `reckon:units` (switch offered, flip keeps the knob, tip once, saved per kind, a bullseye in feet scores 100, flip back on the reveal, distance stays metric, the next metres question opens in feet, ten bullseyes still make 1,000, recap in the chosen units).

## Site code ships through a pull request (21 Oct 2026, Alec's call)
- **What:** any change to the site's code: pages (`*.html` at the root, `board.html`, `admin.html`…), `dn-*.js`, `front.*`, `sw.js`, `engines/`, `assets/`, `tools/`, `tools/tests/`, `.github/`, `package*.json`, `SITE.md` and `toolchain/` docs. **Not** puzzle or news content: new or regenerated files in `reports/`, and the scheduled tasks (Daily news, Pinwheel clean-up, Mini clue nights, Link re-edit), keep pushing straight to `main` as before, after their own checks (`node tools/tests/content.js --all` for puzzles). A commit that mixes the two goes through a pull request.
- **Why:** a push to `main` publishes, and one failing check holds back the whole site. A pull request is tested on GitHub's machines first (the Tests workflow's `regression` job runs the full required suite, `npm test`, on every pull request and never deploys), so a broken change stays off `main`. It is also faster than a full local run: a small cloud workspace can't run the five test groups at once (21 Oct 2026: browsers crashed on 2 CPUs), and `DN_TEST_JOBS=1` takes about 40 minutes.
- **How (Claude):**
  1. Commit on a topic branch made from an up-to-date `main` (`git fetch origin main && git rebase origin/main`), run the focused tests for what changed locally, and push the branch: `git push origin HEAD:refs/heads/<topic>`.
  2. Open the pull request with the REST API (gh's GraphQL commands such as `gh pr create` and `gh pr merge` are refused in Claude sessions): `gh api repos/alecldarlow-cell/dailynoodle/pulls -f head=<topic> -f base=main -f title='…' -f body='…'`. Say what changes for players and what was tested.
  3. Wait for the `regression` check: `gh api repos/alecldarlow-cell/dailynoodle/commits/<sha>/check-runs --jq '.check_runs[] | [.name,.status,.conclusion] | @tsv'`.
  4. **Green:** Claude merges it without waiting for Alec (his call): `gh api -X PUT repos/alecldarlow-cell/dailynoodle/pulls/<n>/merge -f merge_method=rebase`. If `main` has moved and can't be rebased cleanly, rebase the branch, push it (the check runs again) and merge once green. The merge is the publish: Build feed builds, runs the suite again and deploys, as for any push to `main` (see Publishing). Confirm that run and the live page before calling it live.
  5. **Red:** fix it on the branch (the check reruns) or stop and report. Never merge a red pull request, and never edit a test, a screenshot baseline or `registry-debt.json` to turn it green.
  6. Delete the branch after merging: `gh api -X DELETE repos/alecldarlow-cell/dailynoodle/git/refs/heads/<topic>`.
- Alec can see every pull request (open and merged) on GitHub, in the repo's Pull requests tab.
