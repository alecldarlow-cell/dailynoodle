sections, publishing, saved progress, tracking). It is the one place these

## Leagues on another browser or app (21 Oct 2026)
- **Why:** Alec saw iPhone players' results missing from the leaderboards. The logs showed every iPhone member joined, posted one result in that sitting, then nothing (Android: 25 board submits in 24 h, iPhone: 0, none rejected). On an iPhone, Safari, each home-screen icon and the browser inside an app (WhatsApp, Messages…) keep separate storage, and the browser WhatsApp opens can be fresh every time. A player joined in the place the invite opened, then played in Safari or the app, where the browser was in no league, so `dn-board.js` rightly sent nothing. Android's in-app tabs share Chrome's storage, so it only hit iPhones.
- **Fix (Alec's go-ahead, 21 Oct 2026):** a personal link. League settings has **Play somewhere else too?** with **Send me my link** (share sheet, or copy) and **Paste a link**; on an iPhone the "You’re in" card after joining offers **Send me my link** straight away, and the join form says to join where you play. The intro screen has "Already in a league on another browser or app?" leading to the paste form (the home-screen app has no address bar).
- **How:** `dn-board.js` `moveLink()` packs the board id (`pid`), the league list and the current league as `b`, plus the puzzle saves and streaks (`digi-<type>-v1`, `-streak`), game saves while they fit in 40,000 characters, and the tracker id `digi.aid` (not if opted out), into the domain-move format: `https://dailynoodle.co.uk/board.html#dnmove=…` (the fragment never reaches a server). `dn-track.js` unpacks it on arrival exactly as for the domain move: saves merge without overwriting newer progress (finished puzzles add up, the better streak wins), so the tick on Puzzles cards, streaks and finish sheets carry over too; the old tracker id goes into `digi.aid.prev` for the history copy. `adoptBoard` then takes over the board id if this browser is in no league (or is the same player), clearing `fill` so the board copies this browser's history in as that player; if it is in a league as someone else it leaves `pend` and the board asks **Which leagues should this browser use?** (Use my link / Keep this one), never silently. After arriving, the board shows "Your leagues are here now". A typical link is a few hundred characters plus saves.
- **Limits:** a one-off copy, not a sync: after that each place keeps its own ticks and streak, while the board counts both (first result per puzzle kept). Each place needs the link once. The link is the player's key, so the page says not to post it in a group; anyone given it could play as that player. Players orphaned before this (joined in an app's browser that's since gone) must join again where they play: the owner can remove their old row first to free the nickname, and the history copy then brings their saved results in.
- Events: `board_key` {act: send | paste | open | take | keep}. Fixed with it: the board page's first events (`board_open`, `board_key` open) waited for nothing and were dropped, because `dn-track.js` loads after the page's script; they now queue until it has loaded, so `board_open` records from 21 Oct 2026 (none before).
- Tests: `tools/tests/browser/board-key.spec.js` (BOARD-KEY-01: joins in "WhatsApp", plays, sends the link, "Safari" with its own earlier finish opens it, both Minis count, the history copy and a new solve go on the board as the same player; BOARD-KEY-02: pasting, a wrong paste, and the keep/take choice). In the release suite (Chromium, with iPhone wording forced on) and the nightly iPhone WebKit job.

## Leagues with a PIN, and the All puzzles table (24 Oct 2026)
- **Why:** nobody used the 21 Oct personal link (no `board_key` events by 24 Oct) and daily board players fell from 6 to 4. Alec's go-ahead after the site review.
- **PIN:** a player can set a 4-digit PIN (optional field on the start and join forms; a "Set a PIN" card on the board until set or "Later" for the day, `noodle-board-pinlater`; League settings › You › Set / Change PIN). In any other browser or app they open the league's invite link and tap **Already in <league>? Pick your name** (or, on the intro, **Already in a league on another browser or app?** with the code), choose their nickname and enter the PIN: `board_claim` returns their board id and `dn-board.js` `claim()` adopts it (or, if that browser already plays in a league as someone else, asks with the existing "Which leagues should this browser use?" card), then the browser's own results are copied in (backfill). The personal link stays as the second way ("Have a personal link instead?"), since it also carries streaks.
- **Limits:** five wrong PINs lock that player for an hour; claims count towards `board.gate('claim')` (10 an hour per address, 300 a day site-wide, in `limits`). PINs are stored salted and hashed (`board.pins`) and never returned; with only 10,000 PINs the limits are the real protection. `board_claim` is the one function that returns a player id, by design.
- **Let back in:** a league owner's player list has **Let back in** next to each player: for 24 hours, once, that nickname can be claimed without a PIN (`members.claim_until`), then the player is asked for a new PIN. For players who never set one or forgot it.
- **All puzzles:** the board's first pill, and the default view when a board is opened without a puzzle (`?p=all`). `board_overall(player, code, date)`: the day and its Monday-to-Sunday week. Each puzzle completed (solved, or a scored round) earns 1 point plus 1 for each league player whose completed result on it was worse, in exactly `board_day`'s order; ties earn the same; failed or revealed rounds count as played with no points. Ranked by points, then puzzles completed. Rows show "N of 8 done" (the week: 8 a day so far). Shared as "🏆 All puzzles · <day>" with the top five.
- Events: `board_pin` {act: set | reset | claim | letback, from}, `board_share` {type: 'all'}.
- SQL: `toolchain/sql/2026-10-24-board-pins-and-overall.sql` (migration `board_pins_and_overall`; also the complete current source of `board_mine` and `board_peek`, which gained `pin` and `players`). Tests: `BOARD-PIN-01..04`, `BOARD-ALL-01` in `tools/tests/backend.test.js`; `BOARD-PIN-E2E-01` in `board-key.spec.js`. `privacy.html` describes the PIN.

## Site code ships through a pull request (21 Oct 2026, Alec's call)
- **What:** any change to the site's code: pages (`*.html` at the root, `board.html`, `admin.html`…), `dn-*.js`, `front.*`, `sw.js`, `engines/`, `assets/`, `tools/`, `tools/tests/`, `.github/`, `package*.json`, `SITE.md` and `toolchain/` docs. **Not** puzzle or news content: new or regenerated files in `reports/`, and the scheduled tasks (Daily news, Pinwheel clean-up, Mini clue nights, Link re-edit), keep pushing straight to `main` as before, after their own checks (`node tools/tests/content.js --all` for puzzles). A commit that mixes the two goes through a pull request.
- **Why:** a push to `main` publishes, and one failing check holds back the whole site. A pull request is tested on GitHub's machines first (the Tests workflow's `regression` job runs the full required suite, `npm test`, on every pull request and never deploys), so a broken change stays off `main`. It is also faster than a full local run: a small cloud workspace can't run the five test groups at once (21 Oct 2026: browsers crashed on 2 CPUs), and `DN_TEST_JOBS=1` takes about 40 minutes.
- **How (Claude):**
  1. Commit on a topic branch made from an up-to-date `main` (`git fetch origin main && git rebase origin/main`), run the focused tests for what changed locally, and push the branch: `git push origin HEAD:refs/heads/<topic>`.
  2. Open the pull request with the REST API (gh's GraphQL commands such as `gh pr create` and `gh pr merge` are refused in Claude sessions): `gh api repos/alecldarlow-cell/dailynoodle/pulls -f head=<topic> -f base=main -f title='…' -f body='…'`. Say what changes for players and what was tested.
  3. Wait for the `regression` check: `gh api repos/alecldarlow-cell/dailynoodle/commits/<sha>/check-runs --jq '.check_runs[] | [.name,.status,.conclusion] | @tsv'`.
  4. **Green:** Claude merges it without waiting for Alec (his call): `gh api -X PUT repos/alecldarlow-cell/dailynoodle/pulls/<n>/merge -f merge_method=rebase`. If `main` has moved and can't be rebased cleanly, rebase the branch, push it (the check runs again) and merge once green. The merge is the publish: Build feed builds, runs the suite again and deploys, as for any push to `main` (see Publishing). Confirm that run and the live page before calling it live.
  5. **Red:** fix it on the branch (the check reruns) or stop and report. Never merge a red pull request, and never edit a test, a screenshot baseline or `registry-debt.json` to turn it green.
  6. Delete the branch after merging: `gh api -X DELETE repos/alecldarlow-cell/dailynoodle/git/refs/heads/<topic>`.
- Alec can see every pull request (open and merged) on GitHub, in the repo's Pull requests tab.
